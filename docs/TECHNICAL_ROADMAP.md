# 技术路线图

当前版本最值得继续投入的，不是角色化 UI，而是研发闭环的技术主链。建议按下面顺序推进。

## 1. 第一阶段：把执行链打通

- 增加代码写回能力，把模型输出真正落成文件
- 给文件写回增加工作区范围限制和变更清单
- 在写回后自动执行 `gofmt`、`goimports`、`go mod tidy`、`go test`
- 失败时生成结构化错误摘要，进入下一轮修复

## 2. 第二阶段：把状态机做实

- 给任务增加 `queued / planning / writing / testing / failed / done` 状态
- 引入重试计数、失败阈值和熔断
- 把状态持久化到 Redis 或本地文件，支持恢复
- 把每轮修复历史与快照关联起来

## 3. 第三阶段：把隔离执行做稳

- 优先统一 Docker 沙箱执行入口
- 固定镜像、挂载范围、缓存目录和超时策略
- 为 `go test`、`go vet`、`golangci-lint` 提供标准动作模板
- 让容器日志、diff 和快照统一进入报告

## 4. 第四阶段：把上下文增强做深

- 继续扩充 RAG 数据源
- 增强 AST 分析，补齐 import、调用链和包依赖摘要
- 按需接入 OCR / 多模态理解，让外部页面信息进入任务上下文
- 把历史运行结果也纳入可检索知识

## 5. 第五阶段：再考虑入口层

- 如果确实有高频使用需求，再补系统托盘
- 如果确实需要跨应用唤起，再补快捷键和通知
- 如果确实有演示需求，再补轻量角色化外观

## 6. 当前不建议优先投入的方向

- 复杂角色动效
- 角色化外观和拟人表达
- 过多浏览器交互包装
- 和核心执行链无关的 UI 微调
