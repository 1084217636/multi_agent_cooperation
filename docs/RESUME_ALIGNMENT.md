# 创新点与简历对齐建议

这份文档的目标只有一个：

- 给你一版现在就能用、而且和当前代码尽量一致的简历表述

---

## 1. 当前对齐度

基于这轮代码后的状态，这个项目和目标简历的对齐度大约在：

`85% - 90%`

已经明显成立的部分：

- 复杂度评估与多 Provider 路由
- RAG 检索与项目文档上下文增强
- AST 静态分析，并已扩展到 import 与基础调用关系
- 工程预检、自动修复轮次、终止策略和快照留痕
- Docker 已接入默认执行链，并输出沙盒验证结果
- Redis 状态恢复
- LangGraph HTTP 阶段编排，已能接管 `planning + codegen`

还没有完全做满的部分：

- LangGraph 仍然是外部 HTTP 图后端，不是本地单进程 LangGraph 运行时
- 自动修复仍以命令级修复为主，不是模型驱动的真实代码 patch 主链
- 还没有把每轮代码修改产物细化成“逐轮 patch / diff”审计包

## 2. 当前最推荐的简历版本

下面这版是我认为现在最适合直接写进简历的版本。

### 2.1 项目标题

项目二：面向 Go 工程的研发智能体

### 2.2 项目描述

面向 Go 单仓研发场景设计 Coding Agent，围绕任务评估、模型路由、上下文增强、自动修复轮次、沙盒验证与结果留痕实现研发辅助闭环。

### 2.3 技术栈

Go、LLM、多 Provider 路由、AST 静态分析、RAG、Docker、Redis、LangGraph 阶段编排、Mock、Snapshot

### 2.4 核心功能

- 设计复杂度评估与模型路由机制，结合任务复杂度、上下文规模与工程关键词选择模型路径，在在线模型失败时自动回退到 mock 链路。
- 设计阶段化工作流，将需求理解、复杂度评估、上下文准备、代码生成、预检修复与结果留痕拆成显式节点，并支持通过 LangGraph HTTP 后端接管 `planning + codegen` 阶段。
- 基于 Go AST 提取包、结构体、函数、import 与基础调用关系，并结合仓内代码/文档检索做上下文增强，减少模型对符号和依赖的编造。
- 设计工程预检与自动修复轮次控制，串联 `gofmt`、`goimports`、`go mod tidy`、`go test`、`go vet`，并在失败签名不变或无新增变更时触发终止。
- 设计 Snapshot 机制记录运行前后文件状态，输出差异、回滚建议、结构化报告与修复轮次留痕，支撑研发过程可追踪与可恢复。
- 接入 Docker 沙盒验证链，在容器中执行工作区验证脚本并回写状态、日志与退出码，为后续局部编译、单测和 Mock 验证提供统一入口。
- 基于 Redis 持久化 workflow、screen 与 latest_run，支持服务重启后的最近运行恢复与状态续读。

## 3. 比较稳的强化写法

如果你想把简历写得再强一点，但仍然保持基本可信，可以用下面这版：

- 基于 Go 实现面向单仓研发场景的智能体原型，构建复杂度驱动的多模型路由、AST + RAG 上下文增强、工程预检、自动修复轮次与沙盒验证主链。
- 通过 import、函数签名、结构体字段与基础调用关系提取，将真实项目符号暴露给模型，降低 Go 工程场景下的类型与依赖幻觉。
- 设计运行前后 Snapshot、自动终止策略、结构化排障与恢复动作，支撑结果可验证、过程可回溯、异常可回滚。

---

## 4. 现在不建议写满的点

下面这些点仍然不要直接写成“已经完整做完”：

- LangGraph 作为本地单进程默认主运行时
- 自动代码修改后自修复再提交已经完全闭环
- Docker 沙盒中局部编译、局部单测、Mock 验证已经稳定落地
- 完整系统级桌面代理或常驻桌面数字员工

更稳的说法应该是：

- `已接入`
- `支持切换`
- `已完成主链基础能力`
- `为后续扩展预留`

---

## 5. 如果你想进一步缩小差距，简历怎么改最合适

你现在最适合的策略，不是继续把简历写得更满，而是把措辞改得更贴近当前代码。

建议保留的关键词：

- 复杂度路由
- AST 静态分析
- RAG
- 自动修复轮次
- Docker 沙盒验证
- Snapshot
- 结果留痕

建议降级的关键词：

- LangGraph 工作流编排
- 自动提交
- 局部单测 / Mock 验证
- 桌面数字员工

## 6. 面试时怎么解释差距

如果面试官追问：

### 6.1 LangGraph 现在是不是主编排

你可以回答：

- 当前项目是“Go 主控 + LangGraph 可切换阶段编排”的模式
- 默认仍保留 Go 内置主链兜底，但 `planning + codegen` 已能通过 LangGraph HTTP 后端接管
- 这样可以兼顾本地可运行性和图编排扩展性

### 6.2 自动修复是不是已经能改代码

你可以回答：

- 当前已经实现命令级自动修复轮次和终止策略
- 重点先落在 Go 工程常见问题的确定性纠偏，比如格式化、依赖整理、编译和 vet 校验
- 模型驱动的真实代码 patch 主链还在继续补

### 6.3 Docker 沙盒是不是稳定可用

你可以回答：

- Docker 验证已经进入默认执行链，并能输出容器日志、退出码和验证状态
- 当前环境里仍有镜像/命令兼容性问题，所以这块我会表述成“已接入主链并完成验证入口”，而不是“完全稳定”

---

## 7. 当前最合适的定位

现在这个项目最合适的定位是：

- “面向 Go 工程的研发智能体原型”
- “带自动修复轮次与沙盒验证能力的本地开发代理”

不建议直接说成：

- “完整 LangGraph 驱动的 Coding Agent”
- “全自动自愈研发数字员工”

前者更真实，也更能经得住追问。
